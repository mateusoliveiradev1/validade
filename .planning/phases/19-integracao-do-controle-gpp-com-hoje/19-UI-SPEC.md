# Phase 19 — UI Design Contract

Visual and interaction contract for connecting terminal `Hoje` resolution to linked Controle GPP records. Generated by `gsd-ui-researcher`; the checker upgrades `status` only after verification.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none; this is an existing React Native surface |
| Preset | not applicable |
| Component library | Existing primitives from `apps/mobile/src/capture/capture-ui.tsx`: `ScreenHeader`, `ScreenSection`, `PrimaryAction`, `SecondaryAction`, `DestructiveAction`, `Field`, `SelectionRow`, `StatusNotice` |
| Icon library | none; preserve the current text-first mobile vocabulary |
| Font | React Native system sans through existing `StyleSheet` usage |

**Visual source of truth:** `apps/mobile/src/capture/capture-theme.ts`, `apps/mobile/src/capture/capture-ui.tsx`, `apps/mobile/src/capture/TodayScreen.tsx`, `apps/mobile/src/capture/TaskResolutionPanel.tsx`, `apps/mobile/src/capture/GppAvariaFlow.tsx`, and the approved Phase 18 UI contract.

**Product scene:** a produce-sector operator uses one hand in a brightly lit aisle, often with unstable connectivity, while physically removing an expiration risk. The interface must make the next physical action unmistakable and must not imply that the central GPP received anything until acknowledgement actually exists.

**Design-system rule:** extend the current restrained, state-rich operational UI. Do not introduce a dashboard kit, a new component vocabulary, a display font, a new icon set, or decorative illustration. Existing primitives keep their internal styles; Phase 19 adds no parallel token layer.

---

## Scope And Phase Gate

- This contract covers `GPP-09`: linked avaria, reaproveitamento, and produção interna records created from an eligible terminal `Hoje` task.
- `Confirmar esgotado` remains a separate terminal action and never creates a GPP record or baixa.
- Internal purchases remain in the separate Controle GPP surface.
- Full central GPP queue and response actions remain Phase 20.
- Realtime refresh hints for `Hoje` remain Phase 21; retain current refresh and fallback behavior.
- Do not change build identifiers, create an APK, push, or deploy the incomplete GPP track through this phase.
- Planning and execution remain gated by verified closure of the Phase 18 `18-06` conflict-discard gap. The UI specification may be reviewed while that gate is open, but implementation must not be represented as unblocked.

## Experience Architecture

### Required Sequence

The linked flow is progressive and stays within the existing `TaskResolutionPanel` route:

1. Operator opens an eligible terminal task from `Hoje`.
2. The panel shows the current task identity, required evidence, and terminal alternatives.
3. `Confirmar esgotado` remains visible as its own alternative. It does not enter the GPP branch.
4. When physical product is found, the operator enters the quantity removed, completes inherited evidence requirements, and explicitly selects:
   `Confirmo que a quantidade informada saiu da área de venda`.
5. Only after that confirmation may the three GPP destination choices appear:
   `Registrar avaria`, `Enviar para reaproveitamento`, and `Enviar para produção interna`.
6. The operator reviews locked product/lot identity, product code, quantity/unit, destination/finality, actor, and consequences.
7. Submitting creates or queues the linked GPP record without changing the already-recorded physical-removal fact.
8. The receipt shows physical-risk state and GPP delivery state as two separate labeled facts.

Do not expose the three GPP destination choices before step 4. Do not use a modal as the primary flow. Use inline progressive disclosure in the existing one-column `ScrollView`; retain `ConfirmationSheet` only for the existing consequential confirmation pattern where necessary.

### Branch Contract

| Branch | Physical effect | GPP effect | Required interaction |
|--------|-----------------|------------|----------------------|
| `Confirmar esgotado` | Resolves according to existing terminal rules only after its confirmation/evidence contract | No GPP record and no baixa | Show explicit consequence copy before confirmation |
| `Registrar avaria` | Removed quantity leaves the sales-area risk | Linked avaria / baixa GPP record | Require removal confirmation, code, quantity/unit, review, and central submission |
| `Enviar para reaproveitamento` | Removed quantity leaves the sales-area risk | Linked reaproveitamento record | Same gated sequence; destination is not editable to an unrelated finality |
| `Enviar para produção interna` | Removed quantity leaves the sales-area risk | Linked produção interna record | Same gated sequence; destination is not editable to an unrelated finality |

### Screen Ownership

| Surface | Contract |
|---------|----------|
| `TodayScreen` | Keep the current safety header, counts, task ordering, and task rows. Add only a compact linked-GPP follow-up section when a removed item still needs code, correction, conflict review, or synchronization. |
| `TaskResolutionPanel` | Own physical-removal confirmation, quantity, inherited evidence, destination selection, locked review, submission, and the immediate two-truth receipt. |
| Controle GPP / `Minhas pendências` | Remains the durable place for retry, conflict correction, and justified local discard. Hoje may deep-link or route there but must not duplicate a Phase 20 queue. |

## Visual Hierarchy

### Terminal Resolution

**Visual anchor:** the physical-removal confirmation is the focal point until it is accepted; after submission, the paired physical-risk and GPP-delivery status notices become the focal point.

The visible order is locked:

1. `ScreenHeader` with the current action and short consequence.
2. Locked task identity: product, code when valid, lot, current location, pending quantity/unit.
3. Quantity removed and inherited evidence controls.
4. Physical-removal confirmation.
5. GPP destination choices revealed only after confirmation.
6. Review summary.
7. One primary submit action.
8. Separate physical and GPP status notices.
9. Secondary back/correction action.

Use one `ScreenSection` per meaningful step, not one card per field. Do not nest cards or place the four terminal alternatives in an identical decorative grid. Use full-width `SelectionRow` controls with title and operational detail.

### Hoje Follow-Up

When any linked GPP record requires action, place a section titled `Pendências GPP após retirada` after the existing Hoje safety/shift header and transient refresh feedback, before active task sections.

The section:

- never increments `riscos na área`;
- never increments the active Hoje task count unless a separate physical conflict actually reopens the risk;
- orders items by actionability: physical implication, missing code, central conflict/rejection, local pending;
- shows at most product, lot, removed quantity/unit, GPP state, and next action in the row;
- uses one section-level `Sincronizar pendências GPP` action when transport-pending records exist, rather than repeating the action on every row;
- routes code/correction items to their preserved draft and routes conflict/retry work to the existing Controle GPP pending surface.

Do not show a success-only GPP section on Hoje. Central-confirmed records may appear in the immediate receipt and existing sent/history surfaces; routine success must not compete with active physical work.

## Component Contract

| Component / pattern | Contract |
|---------------------|----------|
| `ScreenHeader` | Reuse without restyling. Body is no more than two short sentences and states the physical consequence before the system consequence. |
| Locked identity block | Use a single bordered `ScreenSection` or existing summary panel. Product and lot are read-only values, not disabled text inputs. |
| Quantity field | Prefill pending quantity and inherited unit. Use numeric keyboard and visible unit. Permit a positive value no greater than pending quantity. |
| Product code | Prefill and lock when valid. If missing/invalid, provide `Field` plus a 48dp `Escanear código` or `Informar código` action; do not unlock product or lot identity. |
| Physical confirmation | Use `SelectionRow` with the exact confirmation sentence and accessible selected state. The next step remains unavailable until selected. |
| Destination choices | Three stacked `SelectionRow` controls, each at least 48dp high, revealed after removal confirmation. Selection is singular. |
| Review | Use compact label/value rows. Show product, code, lot, quantity/unit, destination/finality, actor, and the two resulting truths. No basic datum may require opening a modal. |
| Primary action | One per visible step. Disable while invalid or sending; keep the label visible and explain the missing prerequisite inline. |
| `StatusNotice` | Use visible title plus consequence text. Critical notices receive alert semantics; other state changes use polite live-region behavior. |
| Hoje follow-up row | Reuse the bordered row rhythm and 48dp target from existing task/sync surfaces, but do not style it as an active risk card. |
| Retry | Use existing idempotent GPP retry path and the exact manual label `Sincronizar pendências GPP`. |
| Local discard | Reuse the Phase 18 destructive action, reason field, and confirmation contract. Never erase the physical-removal receipt. |
| Loading | Keep the surrounding form and identity visible. Use short loading copy or skeleton-like rows; no spinner-only full screen. |

### Interactive States

Every new control must define:

- default;
- pressed;
- selected where applicable;
- visible focus/accessibility focus;
- disabled with explanatory text;
- loading/sending;
- validation error;
- success, warning, and critical status where stateful.

Use the existing pressed, selected, disabled, warning, and critical tokens. Do not invent hover-only behavior for the mobile-primary surface.

## Quantity And Partial Removal

- Prefill the task's pending quantity and unit.
- Allow reduction only for the quantity physically removed.
- A partial withdrawal creates a GPP movement for that removed quantity and keeps the remainder active in `Hoje`.
- Before submission, show:
  `Você está retirando {removedQuantity} {unit}. {remainingQuantity} {unit} continuará como risco ativo em Hoje.`
- After partial submission, the receipt must show two lines:
  - `Retirada confirmada: {removedQuantity} {unit}`
  - `Permanece em Hoje: {remainingQuantity} {unit}`
- Never render a partial withdrawal as a resolved whole-task success.
- A quantity above the pending amount blocks submission with:
  `A quantidade informada é maior que a pendente. Corrija o valor ou reconfira o lote antes de continuar.`
- The correction/reconference path must preserve history. Do not silently clamp the entered value.
- Different lots always remain separate visible movements even when product codes match.

## Product Code And Locked Provenance

Product, product code, source task, lot, unit, actor, and idempotency provenance must remain visible through review and retry.

| State | Contract |
|-------|----------|
| Valid code | Show `Código do produto` as a read-only review value. |
| Missing/invalid code before removal | Block progression to GPP submission and offer scan/manual entry. |
| Missing/invalid code after removal | Preserve physical removal and show the exact state `Falta informar o código`; never label it `Pendente neste aparelho`. |
| Corrected code | Show the retained source product/lot identity beside the entered code before resubmission. |

Supporting body for the incomplete state:
`A retirada da área de venda foi registrada. Informe ou escaneie o código para concluir o envio ao GPP.`

Primary recovery action: `Informar código`.

Secondary recovery action when camera support is available: `Escanear código`.

## Two-Truth Status Contract

The immediate receipt and every later linked status must expose these facts separately:

| Fact | Label | Allowed values |
|------|-------|----------------|
| Physical sales-area state | `Área de venda` | `Retirada confirmada`, `Retirada parcial — ainda há quantidade ativa`, or `Revisão física necessária` |
| GPP delivery state | `Envio GPP` | `Falta informar o código`, `Enviando para central`, `Pendente neste aparelho`, `Corrigir envio`, `Conflito de GPP`, `Registrado na central`, or `Registro já confirmado na central` |

Rules:

- Physical risk resolves immediately after valid explicit removal confirmation for the removed quantity; it does not wait for GPP acknowledgement.
- GPP success copy is allowed only for `central_confirmed` or `replayed`.
- A real transport/reachability failure after valid data may show `Pendente neste aparelho`.
- Validation, permission, feature, or business-rule rejection shows `Corrigir envio`, never offline pending or central success.
- A GPP rejection does not automatically reopen a physically resolved risk.
- Reopen a Hoje risk only when conflict data indicates product or quantity may still remain in the sales area. In that case show `Revisão física necessária` as the physical fact and return the affected quantity to the active risk list.
- A retry reuses the original idempotency key. Do not use animation, duplicate toasts, or count changes to imply a second record.
- Local discard removes only the unsent GPP attempt after justification; the physical-removal fact and audit history remain visible.

### Status Treatments

| State | Tone | Visible consequence |
|-------|------|---------------------|
| `Retirada confirmada` | success | `A quantidade informada saiu da área de venda.` |
| `Retirada parcial` | warning | `A quantidade restante continua ativa em Hoje.` |
| `Falta informar o código` | warning | `A retirada foi registrada, mas o envio GPP ainda precisa do código.` |
| `Enviando para central` | neutral/info | Disable resubmission and retain the review summary. |
| `Pendente neste aparelho` | warning | `A central ainda não recebeu este registro. Sincronize quando a conexão voltar.` |
| `Corrigir envio` | critical | Preserve submitted values and show the central reason plus `Revisar e corrigir`. |
| `Conflito de GPP` | critical | Show submitted data beside current central data; offer correction/retry or justified discard. |
| `Registrado na central` | success | Show central acknowledgement time when available. |

State is never communicated by color alone. Every treatment combines explicit text, structure, and accessible semantics.

## Confirmar Esgotado Contract

`Confirmar esgotado` remains visually separated from the three GPP destination choices.

- Show it before entering the found-and-removed GPP branch or as an explicit alternative above that branch.
- Detail copy:
  `Use somente quando o produto vendeu ou esgotou antes da retirada. Esta ação não cria baixa ou registro no GPP.`
- Preserve any evidence or confirmation requirement imposed by the source task.
- Use the existing confirmation pattern with product, lot, actor, and consequence.
- Final CTA: `Confirmar esgotado`.
- Do not use destructive red styling; it is consequential but not a destructive-record action.
- After confirmation, do not display a GPP receipt, pending label, or GPP success.

## Typography

Use the current system sans and fixed product-UI scale:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label / metadata | 14px | 400 or 600 | 20px |
| Body / action | 16px | 400 or 600 | 24px |
| Section heading / primary row action | 20px | 600 | 25px |
| Screen verdict / title | 28px | 600 | 34px |

Rules:

- Exactly two new-text weights: 400 and 600.
- Do not add uppercase tracked eyebrow labels, display fonts, fluid type, or condensed data styles.
- Reused components such as `ScreenHeader` retain their established internal typography; do not fork them just to approximate this scale.
- Product, lot, quantity, and current state use at least 16px. Supporting timestamps and actor metadata may use 14px.
- Keep operational body copy short and left-aligned.

## Color

Use current values from `capture-theme.ts`:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `captureColors.background` `#F3F6F1` | Screen canvas and quiet separation |
| Secondary (30%) | `captureColors.surface` `#FFFFFF`, `surfaceMuted` `#EAF1EC`, `surfaceRaised` `#FBFCFA` | Existing sections, locked summaries, rows, inactive choices |
| Accent (10%) | `captureColors.accent` `#0F6B3B`, `accentSoft` `#D7EBDE` | Current primary action, selected destination/confirmation, focus, central-confirmed success |
| Warning | `warningSurface` `#FFF7E2`, `warningBorder` `#D7B75E`, `warningInk` `#574006` | Partial removal, missing code, local pending, stale/retry state |
| Info | `infoSurface` `#E9F2FF`, `infoBorder` `#AFC7E8`, `infoInk` `#183D66` | Neutral transport progress or supporting explanation |
| Destructive | `critical` `#9D2118`, `criticalSurface` `#FFF0EE`, `criticalBorder` `#E1A39C` | Central rejection, conflict, physically meaningful reopen, justified discard |

Accent is reserved for:

- the single current primary action;
- selected physical-removal confirmation;
- selected GPP destination;
- visible focus/selection treatment;
- centrally acknowledged success.

Do not use accent for every row, count, code, or GPP label. Do not use critical styling for ordinary urgency, `Confirmar esgotado`, or transport-only pending. Preserve WCAG 2.2 AA contrast with the existing paired ink/surface tokens.

- Never say `Registrado na central` for local pending, validation failure, permission failure, or conflict.
- Never use `Pendente neste aparelho` for missing product code or any central business rejection.
- Never describe a GPP delivery problem as proof that product remains in the sales area.
- Never describe physical removal as proof that the GPP received the record.

## Motion And Feedback

- Motion conveys only state progression: revealing destination choices after removal confirmation, revealing review, and replacing sending state with its result.
- If animation is used, duration is 180ms with an ease-out curve; animate opacity/transform only, never layout-heavy properties.
- Respect reduced-motion preference by revealing or replacing content instantly.
- No page-load sequence, bounce, confetti, pulsing urgency, decorative shimmer, or new animation dependency.
- Sending feedback stays inline with the review and disables duplicate submission.
- Do not rely on toast-only feedback. The two-truth receipt remains on screen until the operator deliberately leaves.

---

## Responsive And Accessibility Contract

- Mobile first, one column, no horizontal scrolling.
- Every actionable row, button, confirmation, compact choice, and icon-only fallback target is at least 48dp high and 48dp wide.
- At narrow widths, action groups stack full width. Do not truncate terminal action labels.
- Product, lot, code, quantity/unit, destination, and both truth states remain readable without opening another surface.
- Use `accessibilityRole="button"` and `accessibilityState` for selected, disabled, and busy states following existing primitives.
- Physical confirmation exposes its selected state and uses its full sentence as the accessible label.
- Critical conflict/rejection messages use alert semantics; retry progress and acknowledgement updates use polite live-region behavior.
- Focus order follows visual order and returns to the newly revealed section heading or first actionable control after progression.
- Validation errors identify the affected field and the required correction; color alone is insufficient.
- Screen-reader labels distinguish `Área de venda: Retirada confirmada` from `Envio GPP: Pendente neste aparelho`.
- Preserve manual code entry when scanning is unavailable or denied.
- WCAG 2.2 AA is the reference. Body and placeholder text retain at least 4.5:1 contrast against their surface.

## Verification Scenarios

1. **Full avaria:** after removal confirmation, avaria choice appears; review shows linked identity; central acknowledgement produces separate `Área de venda: Retirada confirmada` and `Envio GPP: Registrado na central`.
2. **Sold out:** `Confirmar esgotado` resolves through its separate confirmation and produces no GPP status or receipt.
3. **Partial removal:** review names removed and remaining quantities; remaining quantity stays active in Hoje after GPP submission.
4. **Missing code:** physical removal remains recorded, `Falta informar o código` appears, manual/scan recovery is available, and no `Pendente neste aparelho` label appears.
5. **Transport failure:** valid submitted record shows `Pendente neste aparelho`; physical removal remains independently resolved; manual sync is available.
6. **Central rejection:** preserved draft shows `Corrigir envio` and the reason; it is not queued or represented as central/local success.
7. **Conflict without physical implication:** GPP conflict remains actionable while the removed risk stays resolved.
8. **Conflict with physical implication:** affected quantity returns to active Hoje risk with `Revisão física necessária`; GPP conflict remains separately visible.
9. **Retry/replay:** retry does not duplicate the row and may show `Registro já confirmado na central` only after replay acknowledgement.
10. **Justified discard:** GPP local attempt is discarded only after reason entry; the physical-removal receipt and audit history remain.
11. **Accessibility:** TalkBack reads destination selection, physical confirmation, errors, and the two truth labels in visual order; all targets meet 48dp.
12. **Reduced motion / narrow screen:** progressive sections appear without required animation and all action labels wrap without horizontal overflow.
